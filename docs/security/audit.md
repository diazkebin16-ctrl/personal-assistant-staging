# Audit Security

Audit evidence is generated by server services, not by an LLM or client. Events are append-
oriented and the normal API exposes only owner-scoped reads with bounded pagination. There are no
update or delete audit routes.

Events record identity references, actor, event type, capability/action metadata, risk,
permission, decision, confirmation, result, reason codes, and optional future correlation IDs.
They do not record raw bearer tokens, passwords, refresh/access tokens, service keys, private
keys, or full private content when metadata is sufficient.

Metadata is structured, recursively redacted with the existing central redactor, and limited to
4 KiB before persistence. Database constraints provide an additional 8 KiB ceiling. A required
audit write participates in the same transaction as an authorization or permission mutation; a
write failure rolls back and fails closed. A future side-effect executor must require committed
auditability before execution.
